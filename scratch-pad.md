## Questions for hiring company

1. Why are you using a custom GQL library in your app instead of a well tested and maintained package? What was the cost/benefit analysis results with that discussion. A lot of the problems mentioned that need solving in the tech test around the fetching/storing/handling of data are solved problems with packages like apollo/urql/tanstack.

## Notes 

1. `useTenantQuery` / `useTenantMutation` are the thin wrappers the spec asks for. They read `tenantId` from `TenantContext` and inject it into every operation, including `refetch` and `mutateData` called with `replace: true`, so no call site passes it. Reading and changing the current tenant is a separate hook: `const { tenantId, setTenantId } = useTenant()`.

2. The theming and design work. I'm aware it said that "visual polish" is explicitly out of scope. I chose to spin up a quick theme and simple design so that I could test the project easier and find anything missing that shouldn't be missing. Without any sort of visual polish, the project would have been more difficult to manually test. It also took very little time to put the theme together. If it took a significant portion of the time alloted, I would have obviously kept stricter to the requirements.

3. Search is one box, but `listDevices` ANDs `imei` and `serialNumber`, so sending the term as both matches almost nothing. Two queries can't be merged under server-side pagination. All digits searches IMEI and anything else searches serial. The catch is that a digits-only serial fragment searches IMEIs instead. In the seed data, searching a numbered tenant-alpha serial's four digits never returns that device: `0013` misses `SN-0013-A` (`-0013` finds it) and returns the unrelated `SN-0017-A`, because its IMEI contains those digits. The empty state names the field it searched, but a false match like that has no such hint. I considered an IMEI/Serial selector beside the input, which would remove the guess at the cost of an extra control, but kept the single search box the spec describes.

4. A new search or page keeps the previous rows on screen, dimmed, until the response lands. History does the same when changing page, so the panel doesn't collapse and move Next out from under the cursor. This lives in the components rather than `useQuery`, so the hook only ever returns data for its current variables. The rows can't cross tenants because the list remounts per tenant, or cross devices because the pullout remounts per device. Pagination is disabled and shows "Page - of -" whenever the total isn't known, which covers a first load, a pending search or filter change, and a failed one. It stays live for page changes, so keyboard users don't lose focus on Next. If a search fails, the old rows and total don't come back, because they'd describe results that aren't on screen.

5. A partial response renders everything that resolved. Missing fields show "Unavailable", and a warning names what failed, so a missing value can't be mistaken for an empty one. Dropping the payload because `errors` is non-empty would hide a valid IMEI and state to report a problem with two other fields. A partial response is never treated as fresh, so it refetches on the next mount instead of being cached for the full TTL. If there's no data at all, the panel shows a plain error instead.

6. A reload keeps the entry's previous errors until the response lands, so a warning or error doesn't vanish during a refetch or retry. Each of the three queries has a manual retry button, which stays in place as "Retrying…" so keyboard focus isn't lost. If the retry succeeds and the button goes, focus moves to that section's heading.

7. `tenantId` lives in `TenantContext` and is injected by `useTenantQuery` / `useTenantMutation`. Reading it from module scope or `sessionStorage` would need no provider, but nothing would re-render when it changed, and the tenant React renders with could differ from the one a fetch sends. With context, both come from the same render. `useQuery` and `useMutation` are still exported from `@/lib/gql`, because the tenant layer needs them, so a component could import them directly. A call without a `tenantId` fails at the mock, but one with a hand-passed `tenantId` would work unnoticed. Every call site uses the wrappers today. A lint rule could enforce that, but I left it out to keep this small.

8. Having `tenantId` in the cache key stops one tenant's entry being read as another's, but the key doesn't remove anything. The previous tenant's rows would stay in memory, and a late response would still be written to them. So a tenant switch now aborts every in-flight request and clears all entries and labels, leaving nothing from the previous tenant. The cost is a refetch when switching back. The spec rules out eviction as a cache feature, but this is tenant isolation rather than memory management.

9. The clear runs inside `setTenantId`, so a switch can't happen without it. An effect on `tenantId` would be wrong: child effects run first, so the clear would abort the new tenant's first requests, and the old data would outlive the commit. The clear and the state change land in one render because the switcher calls `setTenantId` from a change event. A caller outside a React event would need to check this still holds.

10. `key={tenantId}` remounts the device list on a switch, which clears the rows, selected device, pullout and debounce timer. It also resets search and the state filter, deliberately. Device sets are disjoint, so a carried-over search would mostly return nothing, and it would send one tenant's IMEI or serial as a query against the other.

11. The device pullout covers the app with a backdrop, and everything behind it is `inert` and can't scroll, so the tenant, page, search and filter can't change while it's open. That's mainly for the lock in 2.3. A tenant switch mid-lock would mean either aborting the mutation, which wouldn't tell us whether the server applied it, or losing the panel that reports a failure, so the user could believe the device was locked. Gating each control while a lock is in flight was the alternative. It needed a global "lock pending" signal read by the switcher and the list. With the backdrop, the only thing a lock has to block is closing the pullout, which is local state. The pullout is portalled to `body` so it stays usable while `#root` is inert.

12. A stale response can't overwrite fresher state, because each set of variables has its own cache entry and `useQuery` only reads the entry for its current variables. When the search or the selected device changes, the hook moves to the new entry in the same render. A late response for the old variables still lands, but in an entry nothing on screen reads. Two requests can't race within one entry either. `load` joins the request already running for that key, and after a `reset` or tenant switch, a response whose request has been removed from the in-flight map is dropped. Aborting on a tenant switch only frees the request. Dropping its response is what stops a leak, because an aborted fetch still returns an error result. All of this lives in the store and hook, so components never handle it. The search debounce cuts the number of requests but isn't what prevents the race. `useMutation` doesn't cache, so it counts calls and only lets the latest one set `loading` and `errors`.

13. The pullout is portalled to `body` for `inert`, not for layering. The backdrop's z-index alone covers the header and blocks clicks, but Tab would still reach the tenant switcher, search and paging behind it, and screen readers could still browse them. `inert` stops both, but it applies to a whole subtree and a child can't opt back out, so `#root` couldn't be made inert while the pullout was rendered inside it. The alternatives were setting `inert` on each sibling, which every new control would have to remember, or rendering the pullout in `App`, which would mean lifting `selectedDeviceId` out of `DeviceList` and resetting it per tenant by hand instead of through `key={tenantId}`. The portal keeps the pullout in `DeviceList` and puts it outside `#root`.

14. The pullout has two action buttons, a Lock/Unlock toggle and Release. Both are always shown, and `listAvailableActions` alone decides whether each one is enabled. The toggle shows Lock if the list offers an action into LOCKED, otherwise Unlock if it offers one into ACTIVE. Release needs an action into RELEASED. Actions are matched by the state they move a device into rather than by ID, which the spec says not to hardcode, or by name, which is display text. The query takes `tenantId` and `stateId`, not a device, so it's cached per state and devices in the same state share an entry. It runs on the confirmed state from the detail, so a rolled-back action doesn't fetch the wrong state's actions. When the toggle has no action to take its label from, the device's state picks the text, so a LOCKED device never reads "Lock device". The mock never offers an action into the state a device is already in, so the one case where `assignAction` fails, locking a device that's already LOCKED, can't be reached by clicking around normally. It happens when the state on screen is out of date: open the same unlocked device in two tabs, lock it in one, then lock it in the other. The buttons use `aria-disabled` rather than `disabled`, so they stay focusable, and a reason line linked with `aria-describedby` says why one can't be used.

15. The optimistic change lives in an overlay, a `{ deviceId → state and policy }` map held in `DeviceList`, which renders both places a device appears, its row and the pullout. Both read their query data with the overlay on top. Rollback is just removing the entry, so the row and the panel go back together. I rejected patching the cache with a snapshot to restore, because a list refetch landing during the action would be overwritten by the snapshot on failure. I also rejected putting the overlay inside the gql store, where `useQuery` would apply it everywhere automatically, because it would tie a generic cache to what a device looks like. `key={tenantId}` clears the overlay on a tenant switch. An action names its new policy but not the policy's ID, which is what picks the badge's tone, so the badge is neutral grey until the confirmed policy arrives. While an action runs, every button is disabled, the clicked one shows "Locking…", "Unlocking…" or "Releasing…", and the pullout can't be closed, so a failure is always seen. A failure, including `assignAction` returning `false`, removes the overlay and shows the server's message in the Actions section until the next action.

16. After a successful action, nothing is refetched beyond the one device. The store gained two generic methods that work on a `queryKey` label. `refresh` reloads the entries a hook is reading, keeping their data on screen, and marks the rest stale. `update` rewrites the data of every entry under a label. The device's detail and history are refreshed, then the confirmed state, policy and last check-in are written into every list entry under `list-devices` that contains the device, and the overlay is removed. This answers "which entry holds `dev-0042`?" by scanning the entries under the list label, which is fine at this size. Invalidating by entity would need the store to index entries by the IDs inside them when they're written, which is the start of normalised storage, explicitly out of scope. If the detail reload fails after the action succeeded, the action's own state and policy are written into the list and detail instead, because the screen shouldn't go back to the old state when it did change. Rows that no longer match the state filter stay in the list until it next refetches, so the table doesn't shift during an action.

17. TODO: a real console should ask for confirmation before a release or a lock, as both affect the customer's handset. I left it out to keep the optimistic update easy to see. With a confirmation step, the optimistic update would start after the user confirms.
